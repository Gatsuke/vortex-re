# Audit: REA Failure Patterns Applied to This Codebase (2026-10)

Status: audit report with an executed fix plan — October 2026.
Method: a full pass over the current codebase (post-Phase-Three, main at
`4777970`) against the five REA failure patterns distilled in the project
owner's cross-category audit of the `morluto/rea` tracker (2,098+ issues
reviewed representatively; the five lessons below are quoted from that
report). This repository has no user-reported issue history yet, so the
issue-history dimension is covered by `docs/UPSTREAM_LESSONS.md`, which
internalizes the REA corpus we fetched and analyzed in October 2026.

The five lessons, as received:

1. **Reliability before feature expansion** — expensive or malformed inputs
   must not crash the application, exhaust memory, or take down an agent
   session (REA #5132 and its containment work; our corpus also carries
   #1563/#1380/#1847/#1911/#1801).
2. **Never report false certainty** — incomplete data must not be marked
   complete; missing evidence must not read as proof that nothing changed.
3. **Cancellation and cleanup must be dependable** — a cancelled request
   stops work, releases resources, and leaves the tool ready for the next
   request.
4. **Integrations must be compatible with real clients** — invalid tool
   schemas, oversized responses, and misleading capability detection break
   working systems.
5. **Testing and evidence infrastructure** — stable identifiers,
   reproducible reports, explicit limitations, cross-platform tests, and
   measurable acceptance criteria keep fixed defects fixed.

## What the audit found already strong (kept, not changed)

* Cancellation: the commit rule (a cancelled run never records `succeeded`,
  never persists after cancellation is observed) is implemented and tested;
  the MCP `notifications/cancelled` bridge is wired into every analysis
  tool; resume-from-checkpoint works after a mid-run cancel.
* Containment basics: every archive read is bounded and budget-accounted;
  native parsers are bounds-checked with hard caps; malformed inputs
  degrade to warnings/limitations at the provider layer; the adversarial
   corpus (text shapes) must end `partial`, never crash.
* Honesty wiring: parser-level "reason" fields flow into limitations and
  warnings; DEX checksum verification is only claimed when the whole file
  was read; ordinals are counted, never fabricated.
* Integration shape: eight MCP tools over one service layer shared with
  the CLI; error parity tests; a response-size budget test (256 KiB) exists.

The findings below are the gaps. Each is ranked by (likelihood of a real
agent session being damaged) × (severity of the damage).

## Risk register

### R1 — HIGH — Misleading capability detection (Lesson 4)

`vortex doctor`'s `supported_now` (correctly) advertises DEX reading,
.NET metadata inventory, and ELF/PE parsing, while `not_supported` still
claims "analyze Android DEX/APK ... DEX files are identified by magic only"
(now factually false), "analyze .NET assemblies: no managed-code provider
is integrated" (contradicts the built-in inventory), and "decompile /
disassemble native executables: no native-analysis provider is integrated"
(misleading — structural native analysis is built in; only
disassembly/decompilation is missing). `vortex_capabilities` merges both
lists into one MCP response, so an agent receives direct contradictions
about what the tool can do. This is REA's "misleading capability
detection" failure mode exactly.

**Fix (Step D):** reconcile the three entries — keep the operation
boundaries honest ("deep X analysis" vs the structural support we ship),
correct the reasons, and add regression tests asserting the contradictory
claims cannot return.

### R2 — HIGH — Oversized responses from Phase-Three finding shapes (Lessons 1, 2, 4)

The bounded-output guarantee was designed around ~1 KiB findings (the
budget test's derivation note says so) and is only exercised by a
text-shaped fixture. The new native/archive findings break that
assumption:

* `pe_imports` details scale as DLL rows × function names, both capped
  only by `max_entries` (request-controllable up to 500) → a single
  finding can carry ~250,000 names.
* `vortex_inspect_artifact` and `vortex_read_evidence` return whole
  findings including details; a 100-item page of fat findings can reach
  megabytes — beyond many real MCP clients' message limits (REA #1850's
  382 KB class search broke clients at a smaller scale).
* `limitations`/`unknowns` are echoed in full in every inspect/search/
  resume response. They are deduplicated but distinct per file
  (each text carries the path), so a 2,000-file directory can produce
  hundreds of KiB of limitations alone.

**Fix (Step E):** absolute record-time caps on `pe_imports` breadth
(≤100 DLL rows, ≤25 names per row, counts and truncated flags always
present), byte-aware item fitting at the MCP boundary (whole items are
kept until a fixed budget, then the page is trimmed with explicit
`byte_capped`/`items_returned` metadata — never silent), a sub-budget for
echoed limitations/unknowns with a pointer to paginated
`vortex_read_evidence`, and a worst-case regression test: a synthetic PE
with 400 DLLs × 500 named thunks inspected through MCP with
`max_entries: 500` (uncapped this is a multi-megabyte response; the
capped response stays under the 256 KiB budget with exact counts and
visible truncation flags). Note the exposure is the single-file inspect
path and `read_evidence` pages: the directory pass identifies native
and archive files by magic only (documented limitation), which its own
honesty note now states correctly (see R1).

### R3 — HIGH — Compare reports diffs without disclosing incompleteness (Lesson 2)

`compare_runs` computes structural diffs but says nothing when a compared
run ended `partial`, `cancelled`, or `failed`. An agent comparing a
complete run against a truncated one reads "findings only in A" as
removals that are really truncation artifacts; comparing two truncated
runs can produce an empty diff that reads as equivalence. There is also
no plain-language note when the two runs examined *different artifacts*
(the `same_artifact_digest` boolean exists, but nothing explains that the
digest difference itself accounts for the diff).

**Fix (Step C):** comparison notes for every non-`succeeded` status on
either side ("its recorded evidence may be incomplete; absence of a
finding is not evidence it was absent"), an explicit warning when
*neither* run is a complete record ("an empty diff is not evidence of
equivalence"), and a note when digests differ. Tests pin all of it.

### R4 — MEDIUM — ELF parse aborts and discards completed work (Lesson 1)

A `.dynsym` section whose `sh_link` strtab index is out of range makes
`elf::parse` return `Err` — throwing away the already-parsed header and
section table (REA #1911's "discard completed results" pattern). Related:
an unresolvable `e_shstrndx` lists sections with empty names and no
reason at all.

**Fix (Step B):** degrade instead of aborting — the bad dynsym becomes an
imports limitation while header/sections survive; unresolvable
`e_shstrndx` sets a dedicated `names_reason` surfaced as a limitation.
Both covered by unit tests built from mutated fixture bytes.

### R5 — MEDIUM — asar member reads trust corrupt metadata (Lesson 2)

`asar::read_member` parses the header's `size`/`offset` with
`.unwrap_or(0)`: a member whose `size` is unparseable yields a "Full"
read of zero bytes (completeness claimed on corrupt metadata), and an
unparseable `offset` reads from the start of the data region — the wrong
member's bytes presented as evidence. The function is currently exercised
only by its own tests (listing is the inspect path), but it is the
documented bounded-read API and will be wired into future passes.

**Fix (Step B):** members whose `size`/`offset` cannot be located are
marked unlocatable at walk time, listed with an error note, and refused
by `read_member` with a precise reason. Test synthesizes a corrupt-header
asar in-process. While implementing this fix, the audit also found the
header-tree walk was bounded in depth but not in total nodes — a single
JSON header with a million file nodes would iterate unboundedly. The
walk is now bounded in three dimensions (depth 64, 10,000 nodes, 100
recorded errors + dropped counters), with the cap disclosed as an
error and `truncated` set.

### R6 — LOW — Four silent caps (Lesson 2)

ELF sections, ELF symbols, DEX classes, and PE DLL rows all disclose
their caps with reasons. Four caps do not: zip safety observations stop
at 50 and listing errors at 10 with no dropped-count; PE thunk
enumeration stops at 10,000 per DLL and export names at 10,000 with no
reason recorded.

**Fix (Steps B/E):** dropped counters surfaced as warnings/limitations;
thunk-cap and export-cap reasons recorded on the parse result; unit tests
including an in-process synthesized "fat PE" that exceeds both caps.
A fourth silent cap surfaced while fixing these (the directory pass's
per-file note for native formats claimed deeper analysis "needs a
native-analysis provider" — false since single-file structural parsing
is built in): the note now distinguishes elf/pe/dex ("structural parsing
is available through single-file inspection") from mach-o/wasm (honest
"not supported in this release"), and a corpus test pins both paths.

### R7 — LOW — Adversarial corpus has no native/archive shapes (Lessons 1, 5)

The service-level "never a crash, never a hang" corpus is text-shaped
(giant line, deep tree, package graph). Native-format adversarial cases
exist only as parser unit tests; nothing guards the full
inspect-a-hostile-directory path (magic + garbage, lying tables, hostile
archive names).

**Fix (Step E):** a corpus case feeding ELF/PE/DEX magic + garbage,
truncated tables, and a traversal-name zip through service-level
`inspect`, asserting honest terminal states and visible limitations.

### R8 — LOW — Windows CI is advisory (Lesson 5)

Every Windows-specific defect in this project's history (the v0.2.0
liveness-probe and path-separator bugs) was caught *after* release
because the Windows job could not block a merge. It has been green on
every commit since; keeping it advisory re-opens exactly that door.

**Fix (Step F):** promote `test-windows` to required. macOS stays
advisory until a maintainer verifies it on real hardware.

## Deliberate non-findings

* SQLite `RunStore` and Rizin integration remain intentionally open
  (ROADMAP Phase Two/Three notes) — not risk items.
* CLI JSON output is not byte-capped by this change: the CLI writes to a
  pipe the user controls, while MCP responses are consumed inside a
  client context window. The service layer both share is unchanged; the
  cap is an MCP-boundary presentation concern. This scoping decision is
  recorded here so it can be revisited if CLI-in-agent usage grows.

## Acceptance criteria for the fix set

1. All existing tests pass, plus new ones for every fix above
   (baseline at audit time: 284 tests, 16 targets, CI green on all five
   jobs at `4777970`).
2. `cargo fmt --check` and `cargo clippy --workspace --all-targets --
   D warnings` clean on Linux and for `x86_64-pc-windows-msvc`.
3. No doctor statement contradicts another; the DEX/"magic only" claim
   is gone.
4. A worst-case single-file PE inspection response (400 DLLs × 500 named
   thunks, `max_entries` 500) stays under the 256 KiB budget ceiling
   with exact counts and visible truncation flags; page trimming, when
   it engages anywhere, is flagged as `byte_capped`.
5. Every compared run that did not end `succeeded` produces a
   comparison note; empty diffs between incomplete runs never stand
   alone.
